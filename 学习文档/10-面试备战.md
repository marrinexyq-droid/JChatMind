## 一、项目介绍（1分钟版本）

> 这个项目叫 JChatMind，是一个基于 Spring AI 构建的 AI Agent 系统，它不是简单的"调 API 聊天"，而是实现了完整的 Think-Execute 自主决策循环。

> 核心功能包括：可扩展的工具调用框架（FIXED/OPTIONAL 双模式）、基于 pgvector 的 RAG 知识库检索、多模型切换（DeepSeek + 智谱 AI）、以及通过 SSE 实时推送 Agent 执行状态到前端。

> 我主要负责：Agent 核心循环的架构设计、RAG 全链路的实现、工具框架的设计、以及前后端交互。

## 二、项目介绍（3分钟版本）

> JChatMind 是一个 AI Agent 系统，后端 Java 17 + Spring Boot 3 + Spring AI 1.1，前端 React 19 + TypeScript + Ant Design X，数据库 PostgreSQL + pgvector。

> **第一个亮点是 Agent 核心循环**。我手动接管了 Spring AI 的工具调用流程：关掉 `internalToolExecutionEnabled`，自己实现 Think-Execute 循环。每次调 LLM 只拿 tool_call，由我的 `JChatMind` 类决定什么时候执行工具、怎么处理结果，支持最多 20 轮的"推理-执行"循环，每一步都有状态管理。

> **第二个亮点是工具框架**。我设计了 Tool 接口 + FIXED/OPTIONAL 分类，用 Spring 的 `@Component` 自动注册，通过 `MethodToolCallbackProvider` 转成 Spring AI 的 ToolCallback。新增工具只需要写一个类 + 加注解，0 行核心代码修改。

> **第三个亮点是 RAG**。文档上传后，先用 Flexmark 解析 Markdown 并按标题分块，然后调本地 Ollama 的 bge-m3 模型生成 1024 维 embedding，存入 PostgreSQL 的 pgvector 扩展，查询时通过 ivfflat 索引做 L2 距离相似度检索。

> **第四是 SSE 实时推送**。Agent 每步运行时，通过 `SseEmitter` 向前端推送 AI_GENERATED_CONTENT / AI_THINKING / AI_EXECUTING / AI_DONE 五种事件，用户可以实时看到 Agent 在做什么。

## 四、面试 TOP 20 问题答案提纲

### Q1: 讲讲项目的整体架构

答：分层架构。前端 React → Controller → Service Facade → 事件驱动 → Agent 核心 → 工具/RAG/SSE。关键是用户消息通过事件驱动异步处理，Controller 不阻塞。

### Q2: Agent 循环是怎么实现的？

答：JChatMind 的 run() 方法执行最多 20 步的 Think-Execute 循环。think() 调 LLM 判断是否需要工具，execute() 执行工具，然后循环直到完成或达到步数上限。

### Q3: 为什么关掉 internalToolExecutionEnabled？

答：为了自己控制循环。默认会自动执行工具，但我需要在每步之间做状态管理、消息持久化和 SSE 推送。

### Q4: 状态机有哪些状态？

答：IDLE → THINKING → EXECUTING → FINISHED / ERROR。由 AgentState 枚举管理。

### Q5: 新增一个工具需要改哪些代码？

答：只需要新建一个类实现 Tool 接口 + @Component + @Tool 注解。核心代码 0 修改。

### Q6: RAG 完整流程是怎么样的？

答：文档上传 → Markdown 解析分块 → bge-m3 embedding → pgvector 存储。查询时：用户问题 embedding → SQL L2 距离检索 → Top-3 结果。

### Q7: 为什么选 pgvector 而不是 Milvus？

答：部署简单，一套 PG 搞定结构化和向量数据，事务一致性，成本低。百万级以内够用。

### Q8: SSE 和 WebSocket 的区别？

答：SSE 服务器→客户端单向，基于 HTTP，浏览器 EventSource 原生支持自动重连。本项目只需要单向推送，SSE 够用且更简单。

### Q9: 多模型怎么切换的？

答：注册表模式。`MultiChatClientConfig` 注册多个命名 Bean，`ChatClientRegistry` 用 `Map<String, ChatClient>` 管理，通过模型名称查找。

### Q10: 为什么要分 Entity/DTO/VO 这么多层？

答：关注点分离。Entity 对应数据库，DTO 是类型安全的业务对象，VO 只包含前端需要的字段。每层互不污染。

### Q11: 用了哪些设计模式？

答：注册表模式、工厂模式、外观模式、策略模式（Tool接口）、观察者模式（事件）、状态机、DTO模式。

### Q12: 项目最大的技术难点是什么？

答：设计 Think-Execute 循环时，需要精确控制工具调用的时机。Spring AI 默认自动执行工具，关掉后需要手动管理 ToolCallingManager，还要在每步中保证消息持久化和 SSE 推送的一致性。

### Q13: 你觉得项目有什么不足？

答：一是没有流式输出，用户体验不够好；二是 RAG 的 chunk 策略太简单，没有重叠窗口；三是 API Key 硬编码，不适合生产。

### Q14: 如果再给你一个月，你会做什么？

答：首先加流式输出，然后改进 RAG 分块策略，第三做 Docker 部署，第四加上用户认证系统。

### Q15: 如果 Agent 20 步还没完成怎么办？

答：目前强制结束。可以改进为返回中间结果让用户选择是否继续，或者支持断点恢复。

### Q16: 并发 100 个用户同时提问会怎样？

答：线程池 core=4, max=10, queue=100。超过 110 个任务会拒绝。可以调大线程池，或者引入消息队列（RabbitMQ/Kafka）削峰填谷。

### Q17: 一个 Agent 实例是线程安全的吗？

答：不是。当前设计是一个请求创建一个 JChatMind 实例，实例之间不共享状态。chatMemory 是实例级别的。pendingChatMessages 是实例级别的 ArrayList，如果多个线程共享同一个 Agent 实例会有并发问题。

### Q18: KnowledgeTools 的 @Tool 注解和 Tool 接口的 getName() 有什么关系？

答：Tool 接口的 getName() 用来在 Java 代码中唯一标识工具（用于 FIXED/OPTIONAL 分类）。@Tool 注解的 name 是给 LLM 看的工具名称。两者可以不同。

### Q19: Think Prompt 里为什么要用 `.system()` 注入？

答：不占用滑动窗口配额，不污染聊天历史，只在本次 LLM 调用中生效。

### Q20: 怎么保证 SSE 消息不会丢失？

答：当前没有一个完美的保证机制。每步中先 DB 持久化再 SSE 推送。如果 SSE 中途断开，用户刷新页面可以通过 GET API 重新加载历史消息。

## 五、面试官可能追问的技术深度

### 关于 Agent

- 如果 LLM 连续返回 tool_call 导致死循环怎么处理？
  答：MAX_STEPS=20 硬限制。每次循环打印日志，如果超过步数强制结束。
- 你觉得还能加什么保护措施？
  答：超时控制（整个 Agent 执行超过 60 秒强制结束）、token 用量限制、同内容工具连续调用检测。

### 关于 RAG

- 如何评估 RAG 的检索质量？
  答：可以计算 recall@k（正确答案是否在 Top-k 中）和 precision@k（Top-k 中多少是相关的）。目前项目没有做评估。
- 如果用户问的问题和知识库内容不匹配怎么办？
  答：LLM 会说"没有找到相关信息"。

### 关于 SSE

- 如果用户刷新页面，正在执行的 Agent 会怎样？
  答：SSE 连接会断开。但 Agent 在后台线程池继续运行（JVM 不重启的话）。用户刷新后会通过 API 加载已有消息。
- 如何处理 Agent 执行完成但前端已断开？
  答：消息已存 DB，下次用户查看会话时正常加载。改进方案：SSE 重连后补发遗漏的消息。
