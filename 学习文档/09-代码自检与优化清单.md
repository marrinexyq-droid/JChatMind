## 一、安全漏洞

### S1: API Key 硬编码（🔴 高危）

**位置**：`application.yaml:22-31`
```yaml
spring:
  ai:
    deepseek:
      api-key: sk-2188cc99eb2e4ecc8558462784667ede  # ← 明文
    zhipuai:
      api-key: 63885f67282d4d1d9b2968fdd55a3156.mOw9PJtTN3boYD7H  # ← 明文
```

**问题**：代码提交到 Git 后 API Key 会泄露。Git 历史中永远删不掉。
**修复**：改环境变量
```yaml
spring:
  ai:
    deepseek:
      api-key: ${DEEPSEEK_API_KEY}
    zhipuai:
      api-key: ${ZHIPUAI_API_KEY}
```

### S2: 邮箱密码硬编码（🔴 高危）

**位置**：`application.yaml:12-13`
```yaml
spring:
  mail:
    password: wkjydaedaibbfdja  # ← QQ邮箱授权码
```

### S3: SQL 注入风险（🟡 中危）

**位置**：`DataBaseTools.java:47-54`
```java
String trimmedSql = sql.trim().toUpperCase();
if (!trimmedSql.startsWith("SELECT")) {
    return "错误：仅支持 SELECT 查询语句";
}
// ↓ 直接拼接执行，有注入风险
List<String> rows = jdbcTemplate.query(sql, (ResultSet rs) -> { ... });
```

**风险**：`SELECT 1; DROP TABLE users;` 这种拼接可以通过校验。
**改进**：用 SQL 解析器校验语法树，或用白名单模式。

## 三、功能缺陷

### F1: 没有流式输出（🟡 中）

当前 Agent 的回复是一次性返回的。用户需要等待完整回复才能看到。
**改进**：用 Spring AI 的 Stream 方式调 LLM，SSE 逐 chunk 推送。

### F2: SSE 没有心跳（🟡 中）

30 分钟超时无心跳，可能被中间件提前断开。
**改进**：定时发送 `heartbeat` 事件。

### F3: SSE 断连不重试（🟡 中）

前端 `es.onerror` 只打日志。
**改进**：3 秒后自动重连。

### F4: 前端无发送状态（🟢 低）

`AgentChatView.tsx` 中的 `setLoading` 未被使用，用户发送消息后没有 loading 指示。
**改进**：发送时按钮变 loading，输入框禁用。

### F5: 没有用户认证（🔴 高）

所有 API 都是公开的，没有登录、没有用户隔离。

### F6: 已禁用的工具仍可作为接口实现存在

`FileSystemTools` 和 `DirectAnswerTool` 虽然 `@Component` 被注释了，但代码还在，容易混淆。

## 四、架构改进建议

### A1: Converter 样板代码过多

4 个 Converter 有大量重复的 Entity↔DTO↔VO 转换代码。
**改进**：用 MapStruct 自动生成。

### A2: Facade 层 CRUD 模板代码

每个 FacadeService 都有 selectAll/insert/updateById/deleteById 的模式。
**改进**：抽象 `BaseFacadeService<T>`。

### A3: 数组类型不统一

后端 Response 返回 `XXX[]`，前端 API 返回 `XXX[]`。TypeScript 中可以统一用 `Array<XXX>`。

### A4: thinkPrompt 硬编码

Agent 的决策提示词硬写在 `JChatMind.java` 里，不能动态配置。
**改进**：存入 Agent 表的 chat_options JSONB 中。
